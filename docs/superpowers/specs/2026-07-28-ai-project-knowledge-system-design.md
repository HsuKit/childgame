# AI 项目知识与迭代追踪体系设计

## 背景

当前项目已经积累了产品代码、Supabase 迁移、题库数据、测试、维护手册，以及 `docs/superpowers/specs` 和 `docs/superpowers/plans` 中的设计与实施计划。Git 历史也能反映具体代码变化。

现有资料缺少统一入口、任务到文档的读取路由和稳定的迭代归档协议。后续 AI 接手任务时，往往需要遍历较多目录才能建立上下文；已有规格、计划、迁移和提交之间也没有统一索引。随着项目继续迭代，这会增加重复分析、上下文遗漏和 token 消耗。

本设计建立一套面向 Codex、Claude Code、Gemini CLI 等编码 AI 的项目知识体系。它不取代代码、Git 或已有规格文档，而是为它们提供轻量、可检索、可持续维护的入口和关联层。

## 目标

该体系需要满足以下目标：

1. 新 AI 能从一个短入口快速理解项目规则，并按任务类型只加载必要上下文。
2. 功能、Bug 修复、数据库、题库和部署等重要改动都有可追溯记录。
3. 可以从业务能力定位到相关代码、测试、迁移、设计、计划和历史迭代。
4. 架构现状与演进历史分离，避免同一事实在多处重复维护。
5. 用模板、索引和轻量校验降低漏记概率，但不使用强制 Git Hook 或 CI 阻塞日常开发。
6. 回填关键历史节点，而不是机械地为每个旧提交补档。

## 非目标

本次不做以下工作：

- 不把 `AGENTS.md` 建成完整项目百科。
- 不复制或迁移已有的 `docs/superpowers/specs` 和 `docs/superpowers/plans`。
- 不为纯格式化、无行为变化的依赖小升级等琐碎改动强制创建迭代记录。
- 不逐个回溯全部历史提交。
- 不通过自动化判断文档内容质量。
- 不在知识文档中保存 `.env`、服务角色密钥或其他私密值。

## 方案选择

### 方案一：单一 `AGENTS.md`

所有项目说明、目录地图、工作流和历史都写入根目录 `AGENTS.md`。这种方式入口简单，但文件会持续膨胀，每次任务都要加载大量无关内容，不符合节约 token 的目标。

### 方案二：分层文档与按需加载

根目录 `AGENTS.md` 只保存强制规则、导航和读取顺序，详细内容拆分到项目概览、架构、目录地图、业务域、迭代和决策文档。该方式最利于按任务加载，但如果没有迭代模板和台账，历史追踪仍可能不完整。

### 方案三：每次迭代建立完整文件夹

每次迭代分别保存需求、规格、计划、实施结果和验证记录。追溯粒度最高，但文件数量和重复内容增长快，维护成本较高。

### 最终选择

采用方案二，并吸收方案三的一页式迭代记录：

- 分层文档负责当前真实状态和按需导航。
- 每次重要迭代只新增一份统一记录。
- 复杂需求继续复用现有 spec 和 plan，迭代记录只做关联与结果总结。
- Git 继续作为精确代码变化的事实来源。

## 文档架构

```text
AGENTS.md
CLAUDE.md
GEMINI.md
PROJECT_INFO.md

docs/ai/
├── README.md
├── project-overview.md
├── architecture.md
├── repository-map.md
├── conventions.md
├── domains/
│   ├── auth-profile.md
│   ├── quiz-question-bank.md
│   ├── companion-shop.md
│   ├── wish-parent.md
│   └── leaderboard-pk.md
├── iterations/
│   ├── README.md
│   ├── _template.md
│   └── YYYY-MM-DD-slug.md
└── decisions/
    ├── README.md
    └── ADR-NNNN-title.md
```

### 根入口

`AGENTS.md` 是所有编码 AI 的统一入口，保持短小，只包含：

- 项目的一句话说明。
- 不可违反的安全、数据和工作流规则。
- 首次读取顺序。
- 任务类型到详细文档的路由表。
- 重要迭代的记录要求和完成清单。

`CLAUDE.md` 和 `GEMINI.md` 是极薄的兼容入口，只要求对应工具先读取并遵守 `AGENTS.md`，不复制核心规则。

`PROJECT_INFO.md` 继续作为面向人的快速手册，但要指向 `docs/ai/README.md`。其中与知识库重复的架构细节应逐步收敛，避免形成第二套事实源。

### 核心现状文档

`docs/ai/README.md` 是知识库总索引，解释每类文档的职责、推荐读取顺序和维护规则。

`project-overview.md` 保存产品目标、目标用户、当前主要能力、技术栈、环境和部署概览。

`architecture.md` 保存系统边界、前端与 Supabase 的数据流、状态管理方式、认证、数据库迁移、题库运行时和部署架构。

`repository-map.md` 保存目录职责、关键入口文件、常见改动位置、测试位置和修改影响范围。它不逐个罗列所有文件，只列稳定边界和高价值定位信息。

`conventions.md` 保存编码、测试、数据库迁移、题库发布、安全、提交和文档维护约定。

### 业务域文档

每个 `domains/*.md` 只描述一个业务域，并使用一致结构：

- 领域职责与边界。
- 主要用户流程。
- 关键页面、组件、store、lib 和数据表。
- 主要数据流与状态变化。
- 不变量和容易出错的约束。
- 相关测试、迁移、工作流文档和最近迭代入口。

业务域文档描述当前真实状态，不保存逐次变更日志。跨域信息只在一个主文档中详细描述，其他文档通过链接引用。

### 决策记录

`decisions/` 使用轻量 ADR 保存长期有效、跨多个迭代且未来可能被重新讨论的重大取舍，例如数据源权威性、奖励结算幂等策略或认证模型。

普通实现选择留在迭代记录中，不为每个小决定创建 ADR。ADR 至少包含状态、背景、决策、原因、影响和替代方案。

## AI 按需读取协议

所有 AI 使用以下读取流程：

1. 首先读取根目录 `AGENTS.md`。
2. 判断任务所属业务域和改动类型。
3. 读取路由表指定的核心文档和业务域文档。
4. 在 `iterations/README.md` 中按业务域、关键词和状态筛选历史。
5. 通常只打开最近一至三个直接相关迭代。
6. 只有需要理解长期技术取舍时才读取相应 ADR。
7. 只有跨领域改动才扩大读取范围。

默认禁止在任务开始时遍历所有迭代、所有业务域或全部 specs/plans。遇到文档无法解释的事实时，再读取代码、测试、迁移和 Git 历史。

任务路由至少覆盖：

| 任务类型 | 推荐读取 |
| --- | --- |
| 页面、路由、状态管理 | `architecture.md`、`repository-map.md` |
| 答题、挑战、错题、题库 | `domains/quiz-question-bank.md` |
| 伙伴、积分、商城 | `domains/companion-shop.md` |
| 愿望奖励、家长报告 | `domains/wish-parent.md` |
| 登录、年级、用户资料 | `domains/auth-profile.md` |
| 排行榜、PK | `domains/leaderboard-pk.md` |
| 数据库与迁移 | `architecture.md` 的数据层章节及相关业务域 |
| 部署问题 | `project-overview.md` 的部署章节及最近相关迭代 |

## 迭代记录协议

### 适用范围

以下改动必须记录：

- 新功能和已有功能的行为变化。
- 影响用户或数据正确性的 Bug 修复。
- 数据库表、RLS、函数和迁移变化。
- 题库结构、生成、校验和发布流程变化。
- 部署平台、环境或发布流程变化。
- 影响多个模块的重构和长期技术决策。

纯格式化、注释修正、无行为变化的小型依赖升级等改动可以只保留 Git 提交。

### 文件与标识

每次重要迭代使用一份 `docs/ai/iterations/YYYY-MM-DD-slug.md`，并分配稳定标识：

```text
ITER-YYYYMMDD-SLUG
```

文件名中的 `slug` 使用小写 ASCII 字母、数字和连字符；迭代 ID 中对应部分使用大写 ASCII 字母、数字和连字符。允许的业务域标识固定为 `auth-profile`、`quiz-question-bank`、`companion-shop`、`wish-parent`、`leaderboard-pk`、`platform` 和 `documentation`，跨域迭代可以填写多个。

同一天同主题继续开发时更新原记录。只有目标或验收标准发生明显变化时才新建迭代。提交信息建议添加 `Iteration: ITER-...`，但不作为提交或校验的强制条件。

### 必填结构

```md
---
id: ITER-YYYYMMDD-SLUG
title: 迭代名称
status: planned | in-progress | completed | paused
domains: [domain-name]
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

## 背景与目标
## 范围
## 关联上下文
## 实施摘要
## 决策与原因
## 验证结果
## 风险与遗留
## Git 关联
```

各章节职责如下：

- 背景与目标：说明为什么做和成功标准。
- 范围：明确本次包含与不包含的内容。
- 关联上下文：链接相关业务域、历史迭代、spec、plan、ADR、迁移或 Issue。
- 实施摘要：记录实际修改的模块和关键文件，不复制代码差异。
- 决策与原因：记录本次关键取舍，长期有效的决策另建 ADR。
- 验证结果：记录实际执行的测试、构建和人工检查及其结果。
- 风险与遗留：明确限制、未完成项和后续建议；没有遗留时明确写“无已知遗留”。
- Git 关联：记录分支、PR 和提交哈希；尚未提交时明确写“未提交”。

### 生命周期

```text
需求确认
  → 在迭代台账登记 planned
  → 开发开始改为 in-progress
  → 按复杂度链接 spec 和 plan
  → 实施与验证
  → 填写实际结果、风险和 Git 关联
  → 状态改为 completed
  → 更新受影响的长期现状文档和 ADR
```

复杂需求可以先产生 spec 和 plan。小型重要 Bug 修复可以直接使用一页式迭代记录，不强制额外创建 spec 或 plan。

原计划与实际结果不一致时，记录差异及原因，不覆盖或改写历史事实。暂停的迭代使用 `paused`，说明暂停原因和恢复条件。

## 迭代台账

`docs/ai/iterations/README.md` 是唯一迭代索引，至少包含：

| ID | 日期 | 状态 | 业务域 | 标题 | 记录 | 关联规格/计划 |
| --- | --- | --- | --- | --- | --- | --- |

索引按日期倒序排列。AI 先通过台账定位，再打开具体记录。业务域名称使用固定集合，避免同一领域出现多种拼写。

## 历史回填

历史回填采用关键节点模式，不逐个提交补档。第一轮预计整理：

1. 项目第一阶段与核心学习流程。
2. 伙伴系统升级。
3. 题库基础设施与各年级题库发布。
4. 匿名登录与伙伴数据恢复。
5. 核心可靠性优化。
6. 错题回顾与家长报告。
7. 儿童友好解析。
8. 选择题答案规范化。
9. 愿望奖励体系。
10. 英语题目难度优化。

每条历史记录优先引用已有 spec、plan、数据库迁移、测试和 Git 提交。无法从仓库确认的内容明确写为“未能从现有资料确认”，不得根据猜测补写。

多个紧密相关的旧提交可以合并为一个能力阶段。对未来定位价值较低的部署触发、文件重编号等提交不单独建档，但可以作为相关迭代的 Git 关联。

## 事实来源与冲突处理

不同资料按以下职责分工：

- 代码与自动化测试：运行行为和接口的事实来源。
- Supabase 迁移：数据库结构和数据演进的事实来源。
- 规范题库 JSON：题库内容的唯一内容源。
- Git：精确差异和提交时间线。
- 核心与业务域文档：当前架构和业务状态。
- 迭代记录：变化原因、范围、结果和遗留。
- ADR：长期技术决策及其理由。
- spec 和 plan：某次复杂需求的设计与预期实施步骤。

文档与已验证代码或迁移冲突时，以代码、测试和迁移为准，并在当前任务中修正文档。无法确认时明确标记未知，不把推测写成事实。

## 轻量校验

新增 `npm run docs:check`，由仓库内脚本执行确定性检查：

- `AGENTS.md`、知识索引和路由表引用的本地文件存在。
- 迭代 ID 唯一且文件名符合约定。
- front matter 的状态、日期和业务域合法。
- 所有迭代文件均出现在台账中，台账不存在失效条目。
- 必填章节完整。
- `completed` 记录包含实际验证结果、风险与遗留说明。
- 业务域文档和 ADR 索引不存在断链。

该命令不评价写作质量，不要求每个 Git 提交都关联迭代，也不通过 Git Hook 或 CI 阻止提交。后续如果实践证明漏记仍然频繁，再单独评估是否加入 CI。

校验失败时，AI 应报告具体文件和原因，修正文档后重新执行。对无法自动确认的语义问题保留人工复核。

## 维护规则

每次重要迭代结束前，执行以下检查：

1. 迭代记录是否反映实际实施和验证结果。
2. `iterations/README.md` 是否已更新。
3. 相关业务域文档是否仍与代码一致。
4. `architecture.md` 或 `repository-map.md` 是否因边界变化需要更新。
5. 是否产生需要独立 ADR 的长期决策。
6. 是否存在敏感信息、失效链接或未经验证的断言。
7. `npm run docs:check` 是否通过。

长期文档只保存当前状态，历史原因只写入迭代记录。链接优先于复制；如果内容必须重复，应指定一个权威来源并让其他位置只保留摘要。

## 实施范围

该体系的首次实施包括：

- 创建根入口和多 AI 兼容入口。
- 创建 `docs/ai` 分层文档、模板和索引。
- 根据当前代码与文档填写项目现状和五个业务域。
- 回填列出的关键历史迭代。
- 添加确定性的文档校验脚本和 npm 命令。
- 更新 `PROJECT_INFO.md`，使其指向统一知识入口。
- 运行文档校验，并检查现有项目测试与构建不受影响。

## 验收标准

实施完成后应满足：

1. 新 AI 只读 `AGENTS.md` 和一个相关业务域文档，就能定位主要代码、数据流、测试和相关历史。
2. 任一核心能力都能从业务域文档定位到相关迭代、spec、plan、迁移和 Git 记录。
3. AI 不需要默认读取全部历史或全部业务域文档。
4. 新重要迭代有统一模板、稳定 ID、状态和台账入口。
5. `npm run docs:check` 能发现断链、重复 ID、缺失索引和不完整的已完成记录。
6. 现有 specs、plans、迁移和工作流文档继续作为原始资料使用，不产生大段重复副本。
7. 所有新增文档均不包含密钥或其他私密值。

## 风险与控制

### 文档随代码漂移

通过完成清单、迭代收尾更新和 `docs:check` 降低风险。业务域文档聚焦稳定边界，避免记录容易频繁变化的逐文件细节。

### 文档数量继续增长

通过一页式迭代记录、业务域固定集合、ADR 使用门槛和历史台账筛选控制规模。默认只读取最近一至三个相关迭代。

### 多 AI 入口内容分叉

`CLAUDE.md` 和 `GEMINI.md` 只指向 `AGENTS.md`。所有规则只在一个权威入口维护。

### 维护流程过重

小型重要修复允许只写简短迭代记录，琐碎变更无需建档；校验只做确定性结构检查，不强制 Git Hook 或 CI。
