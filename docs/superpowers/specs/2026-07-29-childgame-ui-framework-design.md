# Childgame 明亮冒险 UI 框架设计

## 背景

当前应用已经覆盖学习、答题、伙伴、衣柜、愿望、排行、PK、错题和家长页面，但界面缺少统一的信息层级：

- 底部导航同时放置 6 个入口，在 432px 的移动端容器中触控目标和标签空间不足。
- 首页大量使用高饱和渐变、大圆角和重阴影，愿望、挑战、PK、今日任务等模块视觉权重接近，学习主线不够突出。
- Emoji 同时承担插画、状态和操作图标，缺少统一图标语言。
- 页面各自组合样式，标题栏、卡片、按钮、加载态、空态和错误态没有稳定模板。
- 浏览型页面与答题等专注流程共用同一底栏，容易在任务中误触离开。

本设计对全部现有页面进行一次性 UI 框架重构，并以完整回归验证作为交付门槛。业务数据、题库、积分、愿望币和伙伴规则不在本次变更范围内。

## 已确认的方向

用户确认以下选择：

1. 整体风格采用“游戏冒险感”。
2. 色调采用 C1“明亮冒险”：浅色学习界面承载长期阅读，地图、任务、伙伴和奖励提供游戏氛围。
3. 底部导航由 6 项缩减为 4 项，衣柜和排行降为二级入口。
4. 改造范围覆盖全部现有页面，不分批交付。
5. 页面框架采用“地图首页 + 标准内页”，不把所有功能包装成重度游戏场景。

## 产品目标

本次 UI 重构需要同时实现：

- 孩子打开应用后能立即识别今日学习主线。
- 1–6 年级用户都能接受整体气质，避免过度幼龄或过度暗黑。
- 伙伴、愿望和排行继续提供激励，但不与核心学习任务争夺首屏注意力。
- 全部页面共享稳定的视觉令牌、布局壳和反馈组件。
- 答题、挑战和 PK 等流程减少干扰和误触。
- 旧 URL、现有业务行为和数据读写保持兼容。
- 移动端、平板和桌面宽度都具备清晰的自适应表现。

## 导航与信息架构

### 一级导航

底部导航固定为 4 项，并始终显示图标和文字：

| 一级入口 | 定位 | 主要路由 |
| --- | --- | --- |
| 冒险 | 学习主线 | `/`、`/quiz`、`/challenge`、`/mistakes`、`/pk`、`/checkin` 及其子流程 |
| 伙伴 | 养成与装扮 | `/companion`、`/companion/select`、`/shop` |
| 奖励 | 目标与荣誉 | 新增 `/rewards` 汇总页、`/wish-shop`、`/leaderboard` |
| 营地 | 资料与家长区 | `/profile`、`/parent-report`、`/parent-wishes` |

原有路由继续有效。`/rewards` 只作为新的奖励汇总入口，不替换愿望商店或排行榜的旧 URL。

### 导航显示规则

浏览型页面继续显示底部导航，包括首页、伙伴、衣柜、奖励、愿望、排行、个人中心、家长页面和普通列表页。

专注流程隐藏底部导航，改用统一的顶部返回或退出控制：

- `/quiz`
- `/challenge`
- `/pk/quiz`
- `/companion/select`
- 全部结果结算页面
- 错题详情等需要连续专注的子流程

具体路由归属和布局模式由集中式 route meta 配置决定，页面组件不自行判断。底栏高亮需要识别子路由，不以路径完全相等作为唯一条件。

### 导航交互

- 每项触控区域至少 48px 高。
- 标签始终显示，不截断、不缩小到不可读。
- 底栏包含 `env(safe-area-inset-bottom)`。
- 活跃项使用单一强调色、轻背景和字重变化，不使用跳动或持续循环动画。
- 区域切换保留各区域的滚动位置；专注流程退出时回到来源页或明确的区域首页。

## 视觉系统

### 视觉原则

“游戏感”主要来自地图、任务进度、伙伴反馈、奖励节点和完成庆祝，而不是让每张卡片都使用高饱和渐变。

界面遵循以下层级：

1. 今日学习主线拥有最高对比度和最明确的主操作。
2. 伙伴和奖励作为辅助激励。
3. 历史数据、排行和设置使用更克制的标准容器。
4. 页面中同时最多保留一个主要高强调区域。

### 语义色

| 令牌 | 建议值 | 用途 |
| --- | --- | --- |
| `primary` | `#5B50D6` | 主要操作、活跃导航、关键进度 |
| `sky` | `#56B6E9` | 地图天空、信息提示、英语区域 |
| `success` | `#42A878` | 完成、成长、正确反馈 |
| `reward` | `#F2B94B` | 积分、宝箱、愿望和奖励 |
| `danger` | `#EF6B6F` | 错误、待订正、危险操作 |
| `background` | 接近 `#F3F6FC` | 全局浅色背景 |
| `surface` | `#FFFFFF` | 卡片、弹窗和底栏 |
| `text` | 接近 `#18213A` | 主要文本 |
| `muted` | 中性蓝灰 | 次要文本、分隔和禁用状态 |

组件只使用语义令牌，不在页面内散落无含义的原始颜色。文字与背景组合需要满足 WCAG AA；状态不得只靠颜色表达。

### 字体与排版

- 中文采用系统圆润无衬线字体栈，优先保证跨设备清晰度和加载稳定性。
- 英文与数字可以使用圆润字形增强游戏感，但不让外部字体成为中文可读性的前置条件。
- 推荐字号层级：12 辅助、14 正文、16 强调、20 区块标题、28 页面标题。
- 正文行高保持 1.5–1.7。
- 数据、分数和计时使用等宽数字，避免更新时布局跳动。
- 长文本优先换行，不通过缩小字号或无提示截断解决空间问题。

### 形状、阴影与图标

- 页面级大容器圆角约 24px。
- 标准卡片圆角约 18px。
- 按钮和输入圆角约 14px。
- 普通卡片主要通过背景与边框分层；底栏、弹窗和主要按钮才使用阴影。
- 导航、按钮和状态操作使用统一的圆角线面 SVG 图标。
- Emoji 只用于伙伴、奖励、庆祝和情绪插画，不作为主要操作图标。

### 动效

- 按压反馈约 160ms。
- 页面和区块进入约 240ms。
- 奖励与完成庆祝控制在约 360ms，并允许立即跳过。
- 动画优先使用 `transform` 和 `opacity`。
- 页面同时只保留 1–2 个关键动效。
- 支持 `prefers-reduced-motion`，减少动态效果时保留状态变化但移除位移、弹跳和大范围缩放。

## 页面模板

全部页面收敛到 6 类模板。

### 1. 地图首页

适用路由：`/`。

首页是唯一高度沉浸的页面，包含：

- 顶部欢迎、连续天数和星星余额。
- 今日知识地图，清楚呈现语文、数学、英语的完成顺序和进度。
- 当前伙伴作为地图同行者，而不是独立占据大面积无任务信息的卡片。
- 每日挑战、错题修炼和 PK 作为地图支线。
- 三科完成后的宝箱或愿望币节点。

首屏必须优先展示学习主线。愿望、排行和家长报告不再以同等级大卡片占据首屏。

### 2. 区域中心页

适用路由：`/companion`、`/rewards`、`/profile`。

结构为统一页面标题、区域概览、核心操作和二级入口。三个页面共享布局，不共享业务数据。

### 3. 列表与管理页

适用路由包括：

- `/shop`
- `/wish-shop`
- `/leaderboard`
- `/mistakes`
- `/companion/select`
- `/parent-wishes`

这类页面共享筛选栏、列表卡片、空态、错误态、分页或加载更多结构。商品、愿望、错题和排行仍使用各自的领域组件。

### 4. 专注答题页

适用路由：`/quiz`、`/challenge`、`/pk/quiz` 和错题详情答题状态。

专注页隐藏底栏，保持：

- 顶部退出与题号。
- 清晰进度。
- 单一题目卡。
- 足够大的答案触控区域。
- 正确、错误、解析和下一题反馈。

装饰元素不得与题目内容争夺注意力。

### 5. 结果与结算页

适用所有 result 路由。

统一展示成绩、正确率、连击、奖励、错误恢复和下一步动作。结算尚未确认成功时不得展示虚假奖励成功状态。

### 6. 数据与家长页

适用路由：`/parent-report`、`/parent-wishes`、`/checkin`。

这类页面使用更克制、更高信息密度的卡片和图表，但继续沿用相同色彩、按钮、标题栏和导航系统。家长区仍是当前同账号 UI 语义，本次不新增家长身份或权限模型。

## 组件与代码边界

### 布局组件

建议新增或重构：

- `AppShell`：全局背景、最大宽度、safe area 和滚动容器。
- `StandardLayout`：浏览型页面和底部导航。
- `FocusLayout`：专注流程顶部控制和无底栏布局。
- `PageHeader`：返回、标题、说明和页面级操作。
- `BottomNav`：4 项导航、子路由高亮和状态保留。
- `RouteMeta`：路由区域、布局模式、标题和返回策略。

### 基础组件

共享基础组件至少包括：

- Button
- IconButton
- Card
- Badge
- Progress
- Tabs 或 SegmentedControl
- Dialog 和 BottomSheet
- LoadingSkeleton
- EmptyState
- ErrorState
- InlineNotice

领域组件继续位于 quiz、companion、shop、wish 等目录，只使用共享基础组件和语义令牌。

### 数据边界

- Zustand store 的职责不变。
- Supabase 表、RPC、RLS 和迁移不变。
- 积分、愿望币、伙伴经验和打卡结算顺序不变。
- 题库内容与 `data/questions/` 不变。
- 不把业务逻辑搬进展示组件。
- UI 重构过程中发现的既有数据正确性问题只记录并单独报告，除非它直接阻断新 UI 的正确显示。

## 状态、错误与恢复

### 加载

- 预计超过 300ms 的区块使用与最终布局一致的骨架屏。
- 页面允许各区块独立加载，单个次要模块失败不应拖垮整页。
- 提交按钮显示处理中并防止重复点击。

### 空态

空态必须包含：

- 当前为什么为空。
- 用户下一步可以做什么。
- 可执行入口，例如选择伙伴、开始答题或返回地图。

### 错误

- 错误文案说明原因和恢复动作。
- 可重试请求提供原地重试。
- 结算失败不得显示已获得奖励。
- 表单错误显示在对应字段附近；多项错误时提供顶部摘要。
- 弹窗必须有明确关闭入口；存在未保存内容时关闭需要确认。

## 响应式与无障碍

- 以 375px 移动端为主要设计基线。
- 768px 以上增加内容宽度和双栏机会，但不在同一层级混用侧栏与底栏。
- 1024px 以上可将底部导航适配为侧边 navigation rail；首轮实现至少保证内容不会被固定在过窄的 432px 手机框中。
- 触控区域至少 44px，核心导航建议 48px。
- 键盘焦点可见，路由切换后焦点进入主要内容。
- 图标按钮有可访问名称。
- 成功、错误和进度同时使用文字或图标，不只使用颜色。

## 回归验证

本次一次性交付必须完成以下验证。

### 自动化验证

```bash
npm test
npm run test:questions
npm run questions:validate
npm run build
npm run docs:check
```

新增测试需要覆盖：

- route meta 对全部路由的区域归属。
- 底栏对一级和子路由的正确高亮。
- 专注流程隐藏底栏。
- 旧深链仍能渲染正确页面。
- safe area 和底栏不会遮挡内容或弹窗。
- 减少动态效果时关键状态仍可见。

### 浏览器巡检

巡检全部页面的加载、空态、错误态和主要操作，并至少覆盖：

- 375px 手机。
- 768px 平板。
- 1024px 桌面或横屏。

重点用户旅程：

1. 首页进入三科答题并完成结果结算。
2. 每日挑战与挑战结果。
3. 错题列表、详情和复习。
4. 伙伴选择、切换、成长、衣柜和商城。
5. 愿望浏览、提交和状态展示。
6. 排行榜与 PK 创建、加入、答题和结果。
7. 个人资料、打卡、家长报告与家长愿望管理。

## 非目标

本次不包含：

- 数据库迁移、RLS 或 RPC 修改。
- 题库结构或内容修改。
- 积分、愿望币、伙伴经验或挑战奖励规则修改。
- 新的家长认证或权限隔离。
- 全新 3D、视频或重资产地图引擎。
- 对既有业务正确性风险进行顺手重构。

## 参考依据

- Material Design 建议底部导航用于 3–5 个同等重要的一级目的地，并避免超过 5 项：<https://m2.material.io/components/bottom-navigation/>
- Apple Human Interface Guidelines 将 Tab Bar 定位为一级区域导航，并强调稳定可见和清晰标签：<https://developer.apple.com/design/human-interface-guidelines/tab-bars>
- Google Building for Kids 强调简单、一致的导航、熟悉图标和足够大的触控目标：<https://developers.google.com/building-for-kids/designing-engaging-apps>
- 设计探索使用项目中可用的 `ui-ux-pro-max` 规则库；额外检索到的公开第三方 skill 中，`sickn33/antigravity-awesome-skills@ui-ux-designer` 具备较高安装量和公开仓库信誉，但本次不需要安装即可完成设计。

## 完成标准

UI 重构完成时需要同时满足：

- 全部现有路由采用新框架，没有遗留的独立旧视觉页面。
- 底部导航稳定为 4 项，页面归属和专注模式符合本设计。
- 首页清楚突出今日学习地图。
- 所有页面使用共享语义令牌、基础组件和状态组件。
- 业务行为与数据接口未被视觉重构改变。
- 自动化测试、构建、文档检查和关键用户旅程巡检全部通过。
