# 四个现有改动文件的可靠性优化设计

## 背景

当前工作区在以下四个文件中包含尚未提交的改动：

- `src/components/companion/InteractiveCompanion.tsx`
- `src/pages/CheckInPage.tsx`
- `src/pages/HomePage.tsx`
- `src/stores/quizStore.ts`

这些改动分别改善伙伴触摸交互、签到月份浏览、首页统计请求和今日答题统计。本轮工作保留这些目标，在不扩展业务范围的前提下补齐边界条件、错误处理、重复逻辑和自动化测试。

## 目标

1. 移动端和桌面端点击伙伴时，每次实际操作只触发一次互动特效。
2. 签到日历按用户本地日期显示，月份切换在月末日期也保持正确。
3. 首页统计不依赖伙伴请求，并在请求失败或组件卸载时安全处理。
4. 答题判定、积分计算、洗牌和统计日期具有单一且可测试的实现。
5. 数据库查询失败能够结束加载状态并向调用方报告错误。
6. 答题记录使用批量写入，减少网络往返，同时跳过前端生成题目。
7. 新增自动化测试覆盖本轮抽取的纯逻辑和关键边界条件。

## 非目标

- 不修改数据库结构、RLS 策略或 Supabase Edge Function。
- 不重做答题页面、签到页面或伙伴页面的视觉设计。
- 不改变现有题量、题型、通关标准和积分规则。
- 不重构其他 Zustand store 或其他业务页面。
- 不处理奖励幂等性的数据库级方案；该问题需要单独设计事务或服务端函数。

## 方案

### 伙伴互动

`InteractiveCompanion` 使用 Pointer Event 统一鼠标、触摸和触控笔输入，不再分别监听 `click` 与 `touchstart`。互动事件创建带递增 ID、坐标和固定图标的特效记录；图标在创建时确定，不受后续连击状态影响。

所有清理计时器由组件持有，并在组件卸载时取消。可交互区域支持键盘 Enter/Space，提供按钮语义和辅助技术可读标签。

### 签到日期与月份

新增纯日期工具，负责：

- 将本地日期格式化为 `YYYY-MM-DD`。
- 返回指定月份的起止日期。
- 从任意日期安全移动到相邻月份的第一天。
- 判断某月份是否为当前月份或未来月份。
- 生成日历网格所需的空白格和日期格。

页面查询月份数据时维护独立加载和错误状态。每次查询带请求序号，只有最后一次请求可以更新页面，避免快速切换月份时旧响应覆盖新响应。未来月份按钮保持禁用。

### 首页初始化与统计

伙伴、签到和积分初始化继续并行触发；今日答题统计只依赖已登录用户，不再等待伙伴数据。统计请求失败时保留零值并显示现有页面，不阻断首页。

异步回调使用 effect 生命周期标记，组件卸载后不再写入本地 state。每日挑战文案与当前结果页实际发放的 200 分保持一致。

### 答题逻辑与数据访问

从 `quizStore` 抽取以下纯函数：

- `isAnswerCorrect`：统一选择、填空、连线和数独答案判定。
- `calculateAnswerReward`：根据正确性和当前连击返回新连击及本题积分。
- `shuffle`：Fisher–Yates 洗牌，返回新数组且不修改输入。
- `getLocalDayRange`：返回本地当天起点和下一天起点的 ISO 时间。
- `countSubjects`：把答题记录聚合为三科数量。

普通答题和每日挑战复用相同判定与计分函数。Supabase 查询统一检查 `error`；出错时恢复 `isLoading` 并抛出错误。成功但没有题目时同样结束加载，由现有页面的加载/异常逻辑继续处理。

保存记录时先过滤 `gen_` 前缀的本地生成题目，再一次性插入剩余记录。空记录直接返回。保留 store 已有公开方法，避免破坏现有页面调用。

## 错误与并发处理

- 题目加载失败：store 清除加载状态并抛出；已有普通答题页进入错误状态。
- 首页统计失败：首页继续显示，统计维持初始值。
- 月份签到失败：日历显示简短错误并允许重新切换月份触发查询。
- 快速月份切换：忽略过期响应。
- 组件卸载：取消本地计时器或阻止异步回调写入状态。

## 测试策略

引入与 Vite/TypeScript 兼容的轻量测试运行器，并优先测试纯逻辑：

1. 1 月 31 日切换到 2 月不会跳到 3 月。
2. 12 月与 1 月之间正确跨年。
3. 本地日期格式不使用 UTC 日期替代。
4. 选择、填空、连线和数独题使用统一判定规则。
5. 错误答案清空连击且不计分。
6. 连击奖励在既有三档规则下正确封顶。
7. 洗牌返回新数组且不修改输入。
8. 科目统计忽略未知科目。

实现遵循测试优先：先添加会因目标函数缺失或行为不符而失败的测试，再补最小实现，最后重构并运行完整测试与生产构建。
