# ADR-0002: 用幂等追加账本保护奖励结算

- 日期：2026-07-28
- 状态：accepted
- 影响域：答题积分、伙伴与商城、愿望币、数据库迁移与 RPC

## 背景

页面重试、网络超时、重复点击和多个完成入口都可能让同一业务奖励或领取动作执行多次。若客户端直接修改余额，或者先读后写却没有数据库约束，并发与失败重试可能造成重复积分、重复冻结愿望币或余额漂移。

仓库已有 `points_transactions` 和 `wish_coin_transactions` 追加式账本；部分带 `reference_id` 的交易有 partial unique index，愿望奖励和状态转换还使用 RPC、事务级 advisory lock 与行锁。客户端也对部分动作做串行化，但这些能力目前并未覆盖所有奖励路径。

## 决策

- 新增或修改任何“可重复触发”或“可领取”的奖励时，使用 append-only transaction 记录业务事实，不直接写一个可变 balance。
- 每次业务发生都生成稳定、可从业务对象推导的 reference；同一业务发生的重试必须复用该 reference，不得在每次尝试时随机生成新 reference。
- 用数据库唯一约束，或在原子 RPC 中用锁、条件更新和唯一约束，共同保证一次业务状态只发生一次。exactly-once 指数据库中同一稳定 reference 或合法状态转换只成功一次，不表示网络请求只发送一次。
- 客户端按钮锁、请求序列化和一次性 ref 只用于改善 UX、降低并发，不替代数据库级正确性保证。
- 积分与愿望币余额均从账本派生；进程内显示值不是可独立写入的真相。

这是一项未来修改必须遵守的目标，也是每日愿望币奖励、部分带 reference 的交易以及兑换批准、拒绝、兑现等较可靠流程所采用的规则；它不表示当前全系统已经完全幂等。

当前已知差距包括：

- 普通答题的逐题积分没有稳定业务 reference，也没有覆盖该路径的数据库唯一约束；重试仍可能追加重复交易。
- 部分客户端 `points_transactions` 查询或 insert 没有检查返回的 `error`，服务端失败后仍可能误更新本地显示余额。
- 愿望提交每次会生成新的 redemption UUID 并再次写入 freeze。只要可用余额足够，重复提交可以创建多个待审核兑换；现有 reference 唯一性不会把这些调用视为同一次业务发生。
- 商城、伙伴和部分完成结算是客户端串行步骤，不是一个数据库事务；客户端串行化只能降低重复触发概率。

## 原因

追加式账本保留了每次收入、冻结、释放和支出的可审计证据，余额可以重算。稳定 reference 加数据库约束，使超时后的安全重试不依赖客户端记忆；原子 RPC 则能把余额校验、合法状态转换和账本写入放进同一事务。三者组合比页面生命周期或按钮状态更能抵抗并发、刷新和局部失败。

## 影响

- 新奖励流程需要同时设计业务 reference、交易 reason、数据库约束或 RPC、合法状态转换、迁移和自动化测试。
- 重试必须安全且可观测：失败应保留可重试状态，调用方要检查错误，并能区分“尚未执行”“已执行”和“结果未知”。
- 账本行代表已发生事实，不得随意 update 或 delete；纠错应追加具有明确原因和 reference 的补偿交易。
- 余额查询、UI 展示和额度校验都应基于同一账本语义，不能新增第二个可漂移的余额真相。
- 测试至少覆盖重复调用、并发调用、失败后重试、唯一约束、非法状态转换和余额重算；涉及 RPC 时还要覆盖事务边界与权限。
- 现有普通答题积分、愿望重复提交和未检查 insert 错误是迁移到本决策目标时应优先处理的风险，不得在文档中描述为已经解决。

## 替代方案

- **客户端直接增减余额**：拒绝。缺少审计轨迹，失败和并发会让服务端与本地状态漂移。
- **先查询是否存在、再写入，但不加约束**：拒绝。两个并发请求可以同时通过检查，read-before-write 不能提供唯一性。
- **只靠按钮禁用或客户端锁**：拒绝。刷新、多标签页、多个入口和网络重试都能绕过单个客户端实例的锁。
